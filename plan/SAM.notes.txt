- Sam functionality

  General remarks. There is quite a bit of functionality to cover. We will move from relatively straightforward
  (hopefully) to more complicated.

  This is perhaps the one area in pick where I cannot completely exclude the possibility of outright bugs,
  I have currently no evidence that such bugs exist, the functionality has been extensively used (counting
  this as a form of testing), so I am agnostic.

  Some data that can be used for testing is found in pick/align .

  1   Implement the pick options that manipulate SAM cigar sequence and offset field to change the alignment view.
      These are
        --sam-aln-context=<N>
        --sam-aln-xy=<X>,<Y>
        --sam-narrow-xy=<X>,<Y>

  The following will have to be elucidated into well-defined items:

  -   Implement pick operators that do not require LUSPUV lookups and are not rbt (region-bound-tally) operators.
  -   Implement the LUSPUV operators aln_ref aln_aln aln_qry aln_rlr aln_qlt and aln_all. This will allow outputting
      alignments.
  -   Implement further LUSPUV operators that are not rbt operators.
  -   Implement the rbt operators

  A note regarding LUSPUV. Pick translates a slew of operators to hash lookups. It should be possible
  to improve this to indexed array access. Additionally pick has a system where only LUSPUV data is computed
  that is needed, as inferred by operator usage. I would like the same in pluk. Pick's system seems to work
  but is not a shining beacon of elegance.

sam_put (separate from the SAM steps; used by the author)

  pick: ^TAG^VALUE,sam_put appends TAB TAG:VALUE to column 12 (the optional fields, merged by
  -O12), changing an input column from inside a compute; it pops two values and pushes
  nothing. TAG may be written XX.T or XX-T for XX:T. On a record without optional fields the
  result starts with a TAB (an empty field 12 followed by the new one).

  Workaround available now (tested in step17): -i with a compute on column 12,
    pluk --sam -A -i '12::__^%09XX%3Ai%3A:4'
  appends XX:i:<POS>. Same leading-TAB quirk as pick on records without optional fields.

  Ideas for a real sam_put:
   a. As an operator with a row effect: the machine collects the TAG:VALUE pairs of a row;
      after the computes the row's column 12 is rewritten with the same splice-and-resplit
      used by the input rewrites (SAMVIEW.design.txt section 3), so @ filters, --demux and
      the output see the new fields. No TAB is added before the first field when column 12
      is empty. Questions: the compute that holds sam_put has an empty value (sam_put pushes
      nothing) and would normally be written without '::'; interaction with an -i compute on
      column 12 in the same run (order: sam_put after all computes); whether a tag already
      present is replaced or a second one added (pick adds).
   b. Sugar for the workaround: an operator that formats TAG:VALUE (handling XX.T), used in
      an -i compute on column 12; leaves the in-place rules untouched but needs -i and the
      column name.
